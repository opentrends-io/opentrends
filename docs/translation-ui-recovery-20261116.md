# 精选标题停留英文：前端恢复读取

日期：2026-11-16。基线：`origin/main` 的 `31bce2c`。状态：本地验收通过，尚未合并、部署；生产发布需要 Ivy 确认。

## 当批验收边界

- 必达：首包翻译状态未知或服务心跳过期后，仍可有限次读取已生成译文；真实页面正确更新标题，已有译文不倒退。
- 边界：保留每个查询会话的 5 分钟、30 次成功读取、3 轮失败上限；不把未知伪装成正在翻译；明确失败、暂停、额度限制继续停止轮询。
- 不做：改变模型、重跑翻译、修改后端存储、增加状态提示行、发布生产或捆绑未批准的统计功能。
- 阻断条件：上述行为不符、已有回归失败、核心页面不可用、错误写入/数据丢失、秘密泄漏或无界请求。
- 收口：定向红测→修复→完整门禁→生产数据页面对照→提交供评审；生产确认后仅发布 Web 并回验。

## 证据与根因

QA 上午看到 The Verge 0/10 中文，稍后 API 已有 9/10 中文。15:14 的本次自然线上复测已经是 The Verge 9/10、TechCrunch 19/20；不能据此声称再次自然复现了上午的大面积故障。不过 75 秒内页面仅请求一次趋势接口，Ars Technica 的未知状态始终没有恢复读取。

`translationPollAt` 原本只轮询排队、运行、重试和等待登记，普通 `unknown` 及过期的 `serviceValidUntil` 都返回空。前端同时有 10 分钟新鲜期、关闭窗口聚焦刷新：一次不完整快照会让页面停止检查，即便后续 API 已有译文。

后端 `translate-news-items.ts` 的译文/状态读取有 3 秒截止时间，失败时返回空结果，再形成 `unknown`；这是代码中确认可达的入口，不是对上午请求日志的实证归因。本次没有取得上午该请求的数据库追踪，因此不把“数据库超时”说成已证实的触发原因。

修复只在 Web 层增加恢复读取判断。未知或过期的观察结果每 10 秒可再读一次，继续使用原有有限预算；共享工作状态定义、指示器、模型和后端保持原行为。GET 只读缓存和持久化状态，不调用模型、不注册翻译任务。

## 已知限制与发布门禁

- The Verge、TechCrunch 各一条接口明确标记 `failed`，需要单独处理翻译任务失败；本修复不会把失败状态伪造成就绪，也不会重新扣模型费用。
- 持续未知最多恢复读取 5 分钟，不承诺所有文章都能翻译成功。进一步缩短后端冷读耗时列为后续项。
- 本次使用正常浏览器、公开接口和本地隔离运行时，没有变更任何生产资源。获得 Ivy 确认后再合并、发布 Web；保留当时生产绑定和回滚版本，验证初次打开、45/75 秒后的标题和 API 一致性。
